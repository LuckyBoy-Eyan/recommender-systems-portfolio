# 项目演进：从 Top3000 原型到全量目录七路召回与 PLE

> 当前正式版本已经升级为 23.5 万事件商品、七路召回、Two-Tower V2 与 PLE V3。本文后半部分保留的 Top3000、四路召回、Shared-Bottom 内容属于早期实验阶段。当前完整过程与指标以[完整实验报告](complete-experiment-report.md)和[结果摘要](results.md)为准。

## 当前最终阶段

```text
Top3000 四路召回 + Shared-Bottom
  -> 23.5 万事件商品全量目录
  -> Category + 有向多步 Transition
  -> 128 维 Item2Vec + FAISS ANN
  -> Two-Tower V2 + 96 个去重困难负例
  -> 七路理论预算 1,180，完整去重后进入精排
  -> 累积标签 MMoE/PLE，选择 PLE 第 9 轮
  -> 冻结三塔权重 0.05/0.30/0.40
  -> 一次性测试对比 PLE 与独立 RRF
```

最终测试中，PLE 的 HitRate@5、Weighted HitRate@5、NDCG@5、MRR@5 分别相对 RRF 提升 2.11、5.37、7.21、8.91 个百分点；RRF 在 Top20/50 和全候选 AUC 类指标上更强。

## 阶段 0：先搭出召回—排序的最小闭环

项目最初的目标是把经典推荐系统拆成两个明确阶段：多路召回先从全量商品中找候选，
排序模型再把候选压缩到 Top-20。早期原型包含 Recent、Popularity、ItemCF 等简单
召回源，候选合并后构造基础特征，再训练分目标排序器。

这个 Demo 阶段首先验证：

- 不同召回源可以使用统一接口返回候选与分数；
- 候选去重后仍能保留每一路的排名和置信度；
- clicks、carts、orders 可以分别训练和评估；
- Candidate Recall 与最终 Weighted Recall 可以分开计算。

它的价值是快速建立完整链路，但不足也很明显：如果数据切分、全局统计和目标标签的
时间关系没有定义清楚，离线结果可能很好看，却无法代表真实推荐效果。

## 阶段 1：把“防数据泄漏”提升为第一原则

项目随后重构数据协议：先按每个 Session 的最后目标时间划分完整 Session，再执行
Leave-Last-Event-Out，而不是先拆事件或随机抽样。每个目标样本只允许使用目标之前的
Session 历史。

更关键的改进是 Point-in-Time 全局快照。Popularity、ItemCF、Item2Vec、商品统计和
排序特征都只能读取：

```text
event_ts < snapshot_ts <= target_ts
```

最终还加入 `max_reference_ts < min_target_ts` 审计和测试。这样做有用，是因为目标事件
即使没有直接成为标签特征，只要进入了共现图、热度统计或 embedding 训练，也会让离线
指标虚高。当前验证和测试各 9 个日级快照全部通过因果性审计。

项目也主动记录边界：Top3000 商品目录仍由全量事件频次确定，属于 transductive catalog；
“严格 Point-in-Time”只描述动态统计和特征，不夸大为整个数据准备过程完全因果。

## 阶段 2：从玩具数据迁移到 RetailRocket

为了让实验可复现且具有真实电商行为，项目接入 RetailRocket，将 view、addtocart、
transaction 映射为 clicks、carts、orders，并按 30 分钟间隔切 Session。

数据准备阶段继续补齐了容易被忽略的边界：

- 过滤后少于三次行为的 Session 不进入预测任务；
- 最大时间戳并列、无法唯一确定下一事件的 Session 整体删除；
- 删除后从后续合格 Session 递补，固定为 20,000 个；
- 数据规模、标签分布和 SHA-256 指纹写入 manifest；
- 14,000 / 3,000 / 3,000 Session 按目标时间切为训练、验证、测试。

最终数据包含 96,516 条事件和 2,802 个实际出现商品。这一步的意义不是追求大数据，
而是把输入数据、标签定义和实验样本固定下来，使后续每个消融都能比较同一批目标。

## 阶段 3：让召回评估先于排序评估

早期系统容易只看最终 Top-20，无法判断问题来自“目标根本没被召回”还是“被召回后
没有排上去”。因此项目增加：

- 每一路 Recall@K；
- 合并 Candidate Recall；
- 按 clicks、carts、orders 分解的 Weighted Candidate Recall；
- 独占命中、候选规模和来源排名特征；
- RRF 作为不训练的融合基线，解决不同召回源原始分数量纲不一致。

召回源也经历了取舍。Co-visitation 与 ItemCF 高度冗余，且没有提供测试集独占命中，
所以从正式链路删除；保留它只会增加图构建和特征成本。最终系统采用 Recent、Popularity、
ItemCF、Item2Vec 四路召回。

锁定测试集上的单路 Recall@20 分别为 Recent `0.6737`、ItemCF `0.4380`、Item2Vec
`0.2197`、Popularity `0.0357`。单路数值不能直接相加，但能解释每一路在候选池中的角色。

## 阶段 4：从简单向量相似扩展到可审计的 Item2Vec

项目使用 PyTorch 实现 Skip-Gram Negative Sampling，并让每个日级快照只用历史 Session
序列训练。点击、加购、购买正样本使用 `1/3/6` 权重，使高价值行为对 embedding 学习
产生更大影响；初始化、数据顺序、负采样器和线程数固定以保证复现。

还做了“排除中心商品全部真实上下文”的负采样实验。这个想法是避免错误地把潜在正
上下文采成负例，但验证结果没有改善：Candidate Recall 从 `0.9213` 降至 `0.9180`，
Item2Vec Recall@20 从 `0.2113` 降至 `0.2093`，Shared-Bottom Weighted Recall@20
也从 `0.9698` 小幅降至 `0.9694`，因此正式配置保持关闭。

这次实验的价值是说明“理论上更干净的负采样”不一定适合当前稀疏数据，最终决策由
同口径验证结果决定，而不是由方法听起来是否高级决定。

## 阶段 5：加入 Hard Negative 和可解释特征

随机负样本通常太容易，不能教会排序器区分相似候选。项目改用真实召回但未命中目标的
商品作为 Hard Negative，并构造五组特征：

1. 召回置信度：各源排名、分数、来源数、最佳排名和 RRF；
2. 商品热度：事件数、Session 数和最近时间；
3. 商品行为：点击、加购、购买及转化率；
4. Session 上下文：长度、去重商品数和最近时间；
5. Session—商品交叉：出现次数、最近交互和距上次出现时间。

为了判断这些特征是否真的有用，项目做了分组遮蔽实验：

| 被遮蔽特征组 | Weighted Recall@20 绝对下降 | 结论 |
|---|---:|---|
| 召回置信度 | 0.01972 | 最重要，排序器主要依赖候选来源质量 |
| Session—商品交叉 | 0.00501 | 提供明确的个性化增量 |
| 商品热度 | 0.00008 | 当前候选内边际作用很小 |
| 商品行为 | 0.00008 | 当前候选内边际作用很小 |
| Session 上下文 | 0 | 在这次遮蔽口径下未提供可见增量 |

这让特征工程从“列了很多字段”变成有证据的贡献分析，也提示下一步应优先优化召回置信度
和交叉特征，而不是继续堆静态 Session 字段。

## 阶段 6：从独立排序器扩展到多任务排序

最初可以为 clicks、carts、orders 分别训练树模型。为了研究三个目标能否共享行为结构，
项目继续实现 Independent MLP、Shared-Bottom 和 MMOE，并解决一个容易出错的问题：
每个 Session 只观测到一种目标类型，未观测任务不能被当成负例。

因此神经排序器使用任务 mask，每行只对真实 `target_type` 计算损失，并按任务内部的
正负样本比例设置 `pos_weight`。Tree 与 Shared-Bottom 使用完全相同的候选、特征和
Hard Negative，确保比较公平。

正式结果为：

| 数据集 | Tree | Shared-Bottom | 差值 |
|---|---:|---:|---:|
| 验证 | 0.9670 | 0.9698 | +0.00273 |
| 测试 | 0.9665 | 0.9668 | +0.00030 |

验证集支持按预定规则选择 Shared-Bottom，但测试差异几乎可以忽略。因此项目保留
Shared-Bottom 作为主模型和多任务实现展示，同时明确结论是“学习排序明显优于 RRF，
Shared-Bottom 与 Tree 基本持平”，而不是夸大多任务收益。

## 阶段 7：验证模型容量是不是收益来源

为了避免只选一个网络宽度，项目固定数据、训练轮数和随机种子，比较 `32×16`、`64×32`、
`128×64`、`256×128` 四种 Shared-Bottom：

| 隐藏层 | 参数量 | Weighted Recall@20 | 训练时间 |
|---|---:|---:|---:|
| 32×16 | 1,411 | 0.96984 | 9.00 秒 |
| 64×32 | 3,843 | 0.96976 | 9.74 秒 |
| 128×64 | 11,779 | 0.96677 | 13.83 秒 |
| 256×128 | 39,939 | 0.96991 | 22.62 秒 |

数值最好的 256×128 只比 64×32 高约 `0.00015`，参数却超过 10 倍、训练时间超过 2 倍。
在单随机种子下，这个差异不足以证明大模型更好，因此正式配置继续使用 64×32。这个实验
有用，因为它把模型选择从“越大越强”改成了效果、稳定性和成本共同权衡。

## 阶段 8：候选 Top50 / Top100 深度消融

扩大候选池看起来应该提高上限，但也会增加特征计算和排序难度。项目固定其余协议，
把每路候选从 50 扩到 100：

- Candidate Recall：`0.9213 -> 0.9360`；
- Weighted Candidate Recall：`0.9784 -> 0.9819`；
- 平均候选数：`119.03 -> 227.95`，增加约 91.5%；
- Shared-Bottom Weighted Recall@20：仍为 `0.9698`；
- RRF Weighted Recall@20：`0.7735 -> 0.6135`。

新增命中主要是 clicks，权重最高的 orders 在 Top50 已达到 100% 候选覆盖；新增目标也
没有被 Shared-Bottom 排进前 20。于是正式配置保留 Top50：几乎翻倍的计算成本没有转化
为主指标收益。详细结果见 [候选深度消融](experiments/candidate-depth.md)。

## 阶段 9：用 Warm-up 修复早期快照历史不足

Point-in-Time 做得越严格，最早训练快照可用历史越少。项目没有直接把更早数据混入标签，
而是增加只用于全局统计、不产生标签的 Warm-up Session，比较 0、3、7、14 天。

Warm-up 确实增加了 ItemCF、Item2Vec 和候选覆盖，但收益并不单调传到最终排序：3 天组
Shared-Bottom 验证指标最高 `0.97450`，比 0 天高 `0.00248`；14 天组候选覆盖最好，
总耗时却从 236.5 秒增到 316.7 秒。一个加购样本就可能明显改变加权指标，且实验只有
一个种子，因此不能声称 3 天稳定最优。

这个实验有用，因为它揭示了三件事：更多历史会替换而不只是增加向量近邻；候选覆盖
改善不保证 Top-20 改善；时间正确性、效果与计算成本必须共同评估。详细结果见
[Warm-up 消融](experiments/warmup.md)。

## 阶段 10：锁定验证方案，只打开一次测试集

当召回源、候选深度、排序器和主要参数确定后，项目在验证集选择 Shared-Bottom，再执行
一次锁定测试评估。最终结果：

| 阶段 | Weighted Recall@20 |
|---|---:|
| RRF 基线 | 0.7770 |
| Tree | 0.9665 |
| Shared-Bottom | 0.9668 |

Shared-Bottom 相对 RRF 绝对提升 `0.1898`、相对提升约 24.43%，但只比 Tree 高
`0.00030`。项目同时把“测试集已经打开，后续不得继续用它调参”写进 README 和报告。
这一步使结果边界比单纯报告最高数字更可信。

## 阶段 11：从实验工作区收敛为可复现项目

最后清除了 300MB 以上可再生成的候选 CSV、排序模型、训练样本和本地数据，只保留源码、
配置、测试、Markdown 报告以及轻量 metrics/manifest JSON。目录统一为 `configs/`、
`docs/`、`results/`、`scripts/`、`src/`、`tests/`。

这个整理没有改变模型指标，但让读者能快速区分“核心实现”“实验结论”和“可再生成
产物”，也避免大文件掩盖真正有价值的代码与分析。

## 最终保留与未保留

| 内容 | 是否进入正式系统 | 原因 |
|---|---|---|
| Point-in-Time 日级快照 | 保留 | 防止目标和未来事件进入召回图与特征 |
| Recent / Popularity / ItemCF / Item2Vec | 保留 | 提供互补候选并可独立诊断 |
| Co-visitation | 不保留 | 与 ItemCF 高度冗余、无独占测试命中 |
| RRF | 保留为基线 | 无训练、可解释，但对候选深度敏感 |
| Hard Negative | 保留 | 比随机负例更接近真实排序难点 |
| Shared-Bottom 64×32 | 保留 | 验证集选中，成本低，展示多任务实现 |
| 更大 Shared-Bottom | 不保留 | 极小单次增益不足以覆盖参数和耗时增加 |
| 每路 Top100 | 不保留 | 候选成本近翻倍，主排序指标无收益 |
| 排除全部正上下文负采样 | 不保留 | Item2Vec 与最终指标均未改善 |
| Warm-up | 保留为研究配置 | 有信号但单种子证据不足，未替换正式测试口径 |

## 如果继续迭代

下一轮更值得投入的方向是：

1. 在新的验证切分上做多随机种子和配对 Bootstrap；
2. 只用训练窗口确定商品目录，消除 transductive catalog 边界；
3. 针对不同召回源搜索不同配额，而不是统一 Top100；
4. 比较 LightGBM LambdaRank 与当前 Tree / Shared-Bottom；
5. 增量物化 ItemCF、Item2Vec 和特征，并测量线上延迟、内存与吞吐。
