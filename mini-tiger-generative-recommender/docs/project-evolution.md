# 项目演进：从生成式 Demo 到可复现实验系统

## 说明

这份记录根据当前仓库保留的代码、配置、测试和实验指标重建。由于早期 Git 提交和
完整对话时间线没有保留，下面描述的是可以由仓库证据支持的“问题—改进—实验—决策”
顺序，而不是逐日开发日志。

## 演进总览

```text
合成数据 Demo
  -> MovieLens 公开数据验证
  -> KuaiRec Big Matrix 主实验
  -> 无泄漏数据与特征协议
  -> 工业 RQ-KMeans Semantic ID
  -> 训练、检查点与 CUDA 工程化
  -> Exact / Trie Beam 双解码与瓶颈诊断
  -> 等容量 SASRec + 多阶段精排
  -> 失败实验复盘与正式版本收敛
```

## 阶段 0：先证明生成式推荐链路能够运行

最初版本更接近一个教学 Demo：生成一小批用户—物品交互，为物品构造层级编码，
再让序列模型根据用户历史逐级预测下一物品编码。这个阶段的目标不是追求有说服力的
业务指标，而是尽快回答四个基础问题：

1. 一件物品能否被表示成多个离散 Token；
2. 后一级 Token 能否依赖前一级 Token 自回归生成；
3. 生成编码能否稳定映射回唯一物品；
4. 训练、评估和测试能否形成一条确定性的端到端链路。

因此保留了 `configs/demo.json`、合成数据模块和快速测试。它们现在仍然有用：真实数据
实验很重，而小 Demo 可以在几分钟内发现张量形状、数据切分、非法 Token 和指标计算
错误，是后续每次重构的回归基线。

## 阶段 1：从“代码能跑”转向“公开数据可复现”

只有合成数据无法说明模型在真实序列上有效，于是项目加入 MovieLens 数据准备脚本和
固定配置，把数据下载、字段标准化、时间排序、训练与评估全部脚本化。同时增加：

- 按用户时间顺序切分，而不是随机拆分交互；
- Semantic ID、随机层级 ID 和 Popularity 对照；
- Recall、NDCG 和 Candidate Recall 等统一指标；
- 已看物品过滤，避免把历史物品当成有效推荐命中。

这一步的价值在于建立了第一套可复现的公开数据协议，也暴露出一个问题：小数据结果
适合验证实现，却不足以支撑“工业生成式推荐”这一项目定位。于是 MovieLens 被保留为
快速回归配置，主实验继续迁移到规模更大、行为更丰富的 KuaiRec。

## 阶段 2：迁移到 KuaiRec，并重新定义真实任务

KuaiRec Big Matrix 没有统一的点击标签，因此项目先把任务定义清楚：观看比例至少
`0.7` 且播放不少于 5 秒才记为正反馈，然后预测每个用户的下一次正反馈视频。

数据处理最终得到 7,174 个用户、9,438 个视频和 6,309,308 条正反馈。为了避免为了
“上大数据”而牺牲实验边界，项目同时确定了：

- 用户级 leave-last-two-out：倒数第二条验证、最后一条测试；
- 训练只读取更早前缀，验证集选择 epoch，测试集只报告最终结果；
- 每位用户保留最近 300 条历史，并限制训练预测点控制单机成本；
- 原始处理文件仍保留全量行为，训练规模由配置决定。

这一步有用的地方不是单纯把数据变大，而是让项目具备明确的任务定义、样本边界和资源
预算。详细协议见 [KuaiRec 实验](kuairec-experiment.md)。

## 阶段 3：让 Semantic ID 真正包含内容与行为信息

早期编码更像对任意 Item ID 做分层编号。为了让“Semantic”不是名字，项目逐步加入：

- 标签、caption 类别、topic tag 和封面文字等静态内容；
- 字符 1–2 gram TF-IDF、离散类别 one-hot 和 TruncatedSVD；
- 只用训练前缀构建的 item-user 协同向量；
- 内容 64 维与协同 64 维拼接、归一化后的 128 维物品表示。

协同特征不能读取验证和测试目标，这是一次重要修正：如果用全量交互构造物品向量，
即使模型训练没有读标签，索引本身也已经间接看到了未来。当前协议把特征生成也纳入
无泄漏边界，因此结果更可信。

## 阶段 4：从树式 KMeans 升级为工业 RQ-KMeans

旧实现会在每个父前缀下重新聚类，能够制造唯一层级编号，但更接近树目录，不是标准的
残差量化。主链路后来改成全局多级 RQ-KMeans：每一级量化上一级未解释的残差，多个
码字共同重构物品向量。

升级不只替换了聚类算法，还补齐了索引工程能力：

- PCA、白化和 L2 归一化；
- Faiss / sklearn 后端自动切换；
- 最大桶容量约束，避免少量粗 Token 过载；
- 最后一级 Hungarian 最小代价碰撞消解；
- 极端情况下的 Tail Token；
- Schema 版本、SHA-256 指纹、码本和预处理参数持久化；
- 碰撞率、Token 利用率、熵、桶大小和重构误差诊断。

最终 9,438 个视频编码零碰撞，三级 Token 利用率均为 100%。Behavior-aware RQ 的
Candidate Recall@200 为 `0.561890`，等容量旧 RQ 为 `0.562169`，没有形成性能提升。
它仍被保留，是因为它提供了更规范的残差量化、可发布索引和公平实验控制，而不是因为
它“刷高了指标”。详细设计见 [RQ-KMeans 设计](rq-kmeans.md)。

## 阶段 5：补齐真实训练所需的工程能力

小 Demo 可以一次跑完，但 KuaiRec 全量训练需要能中断、恢复和稳定比较。项目因此加入：

- CUDA、Apple MPS 和 CPU 自动选择；
- AdamW、梯度裁剪和混合精度；
- 每轮验证、按 Recall@20 选最佳状态和 patience 早停；
- checkpoint 保存与跨 CPU/CUDA 加载；
- 训练曲线、配置、索引指纹和结果指标共同落盘；
- Windows NVIDIA 环境的独立复现说明。

这些改进本身不保证更高离线指标，但能减少“某次偶然跑出来、后来无法恢复”的风险，
也是把实验原型变成工程项目的必要步骤。

## 阶段 6：约束解码，并判断搜索是不是瓶颈

生成多个 Token 后，朴素 Beam Search 可能组合出商品目录中不存在的编码。项目构建了
真实商品编码 Trie，只允许沿合法前缀扩展；同时实现分块全目录精确打分，作为搜索上界。

实验中 Exact 与 Beam=500 的 Recall@200 都是 `0.561890`。这条结果非常重要：它说明
继续扩大 Beam 不会解决当前问题，搜索剪枝不是主要瓶颈。逐级诊断进一步发现，第一级
粗 Token Top-1 约为 9%、中位排名约为 13，而后两级更容易预测，问题被定位到粗路由。

这类诊断比只报告最终 Recall 更有用，因为它把下一步优化从“调 Beam 参数”转向
“改善第一级可学习路由或历史编码器”。

## 阶段 7：把生成模型放进多阶段推荐系统

纯生成模型负责召回，但它不一定擅长在 Top-200 内做精细排序。因此项目增加 SASRec
Item-ID 基线和候选精排，并把生成模型与 SASRec 都控制在约 163 万参数，避免容量差异
被误认为方法收益。

正式测试结果形成了清晰的阶段贡献：

| 阶段 | Recall@20 | NDCG@20 | 作用 |
|---|---:|---:|---|
| 纯生成召回 | 0.196822 | 0.095620 | 验证 Semantic ID 能生成有效候选 |
| 固定融合精排 | 0.213131 | 0.104453 | 验证 Item-ID 行为信号能改善候选顺序 |
| 学习式精排 | 0.213688 | 0.104760 | 学习生成分、SASRec 分和上下文的组合 |

学习式精排的增益不大，但方向一致；它没有改变 `0.561890` 的 Candidate Recall@200，
说明召回与排序的责任边界是清楚的。完整指标见 [实验结果](results.md)。

## 阶段 8：用失败实验排除看似合理的方向

定位到第一级路由后，项目尝试了两个直接方案：

| 实验 | 假设 | Candidate Recall@200 | 决策 |
|---|---|---:|---|
| 第一级损失权重 ×2 | 强化粗 Token 监督可以提高路由 | 0.539309 | 下降，移出主链路 |
| SASRec 粗 Token 蒸馏 | 更强教师可以迁移粗路由知识 | 0.539030 | 下降，移出主链路 |

SASRec 教师的第一级 Top-1 达到 `18.40%`，但学生只有 `8.92%`，说明教师信号本身
有信息，当前固定路由和 KL 蒸馏方式却没有让学生吸收。失败实验的价值是阻止项目继续
围绕同一种损失反复微调，并把后续方向收敛到可学习、负载均衡的粗路由。

## 阶段 9：从实验目录收敛为可复现项目

最后一次改进不是模型改进，而是证据和结构改进：删除本地数据、checkpoint、临时输出
和 Windows 传输副本；把源码、配置、测试、正式指标与文档分开；保留失败实验结论但不
保留无法复现价值的中间文件。

当前项目希望展示的不是“每个尝试都成功”，而是完整的问题解决过程：先建立可运行
基线，再提高数据与评估可信度，随后升级索引和训练工程，最后通过诊断和消融决定哪些
方法应该进入正式系统。

## 最终保留与未保留

| 内容 | 是否进入正式系统 | 原因 |
|---|---|---|
| 合成 / MovieLens 快速配置 | 保留 | 低成本回归与公开数据复现 |
| KuaiRec leave-last-two-out | 保留 | 主实验协议，时间边界清楚 |
| Behavior-aware RQ-KMeans | 保留 | 索引质量、发布能力和公平控制更完整 |
| Trie Beam + Exact 诊断 | 保留 | 保证合法生成并定位搜索上限 |
| SASRec 固定融合 | 保留 | 带来明确的 Top-20 排序收益 |
| 学习式精排 | 保留 | 小幅改善候选内部排序 |
| 粗 Token 损失加权 | 不保留 | Candidate Recall 明显下降 |
| SASRec 粗 Token 蒸馏 | 不保留 | 教师信号未有效迁移 |

## 如果继续迭代

下一轮不应继续无目的地扩大 Beam 或调整粗 Token 损失权重。更有价值的方向是：

1. 可学习且带负载均衡约束的第一级路由；
2. 更强的生成历史编码器，并保持与基线等容量；
3. 正反馈阈值与更多随机种子消融；
4. 增量物品索引、线上延迟和吞吐测试；
5. 百万级目录下的分布式训练和候选服务。
